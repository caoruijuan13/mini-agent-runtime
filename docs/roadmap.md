# 学习与项目优化路线图

更新时间：2026-09-09。本文是计划，阶段完成情况必须由后续代码和实验确认。

## 方向与节奏

以 **Agent runtime 为主线，AI 服务可靠性与性能为基础**，用现有 Rust 网关 + Python Agent 项目验证长期方向。沿用此前“不急于找工作，先积累知识并深入研究”的偏好；方向可以在实践后调整。

目标是能独立解释并验证：一个 Agent 任务如何执行、如何停止、崩溃后如何恢复、过载时如何保护资源，以及如何区分模型问题和运行时问题。

暂按每周 8–12 小时、约 20 周安排；这是学习预算估计，不是交付承诺。每周约 30% 学原理、50% 做实现和实验、20% 复盘。时间不足时延长阶段，按验收结果推进。

## M0：理解链路和建立基线

**学习内容**：Token、上下文窗口、消息角色、工具调用、finish reason、采样随机性；区分模型生成、工具执行和网关转发。结合现有经验补齐 Tokio Future、流的拉取过程和 HTTP/SSE 生命周期。

**项目工作**：

- 跟踪一个纯文本任务和一个多轮工具任务，标明每一步输入、输出和状态归属。
- 运行现有隔离 QA 和完整 Mock 基准，保存环境、代码版本、工作区差异和原始报告。
- 梳理故障矩阵：无效参数、未知工具、模型断流、工具卡住、重复调用、最大轮数耗尽。
- 记录 Mock 与真实模型的差异，识别演示工具的数据来源与能力限制。

**验收**：能够不依赖代码助手讲清整条链路；隔离 QA 没有跳过集成测试；完整基准满足既有重复性契约，失败则记录并定位原因。形成一页现状说明和排序后的问题清单。

## M1：执行正确性与端到端流式

**学习内容**：SSE 帧与网络分片的区别、增量 UTF-8 解码、工具参数分片组装、状态机与协议不变量。

**项目工作**：

- 已将普通执行逻辑收敛到 `AgentRuntime`；后续为它定义独立的流式事件状态机，不再在应用层复制循环。
- 定义内部事件：文本增量、工具调用增量、工具结果、结束、错误；携带 run ID、step ID 和必要的调用 ID。
- 打通 Provider → Rust → Python → CLI 的真实流式链路，避免为了判断工具调用而先请求完整回答。
- 按调用索引/ID 组装工具名称和参数；参数完整并通过 Schema 验证后才执行工具。
- 统一工具定义来源，区分“模型提出调用”“参数合法”“工具执行成功”。非法 JSON 不再静默变成空参数。

**故障实验与验收**：

- 覆盖中文跨字节分片、多个 SSE 事件同块到达、单个事件分多块到达、多工具交错增量、非法参数和中途断流。
- 使用可控延迟的模拟上游，证明首段输出在完整生成结束前到达，不能靠本地逐字显示通过验收。
- 每个完整调用至多执行一次；不完整参数不能执行；异常结束不能被记录成成功。
- 明确定义 finish reason 与工具调用字段冲突时的协议错误行为，保持普通/流式路径一致。

## M2：超时、取消与工具执行边界

**学习内容**：总截止时间与单次 I/O 超时、协作式取消、资源所有权、阻塞调用、进程隔离、重试的适用边界。

**项目工作**：

- 为一次 run 定义总时间、最大步数和输出预算；模型调用、工具执行与后续排队共享剩余时间预算。
- 传播用户取消和客户端断开信号，关闭流、连接和关联任务，并写入明确终态。
- 为网络、协议、参数、工具、超时、取消建立结构化错误，过滤密钥和不必要的上游正文。
- 增加请求大小、消息数量、工具参数/输出大小限制；制定工具白名单与敏感操作授权接口。
- 先给合作式工具增加取消检查；需要强制终止的工具放到可管理子进程中。取消等待不能视作终止执行，子进程也不等于完整安全沙箱。
- 只对可安全重试的暂态失败使用有上限的退避和抖动；重试仍消耗同一总预算。已有部分输出的流式请求不自动透明重放。

**故障实验与验收**：分别在模型等待、流输出、工具执行期间取消；注入永不返回的上游、慢工具和连接中断。每次都检查终态、连接、后台任务、子进程和资源计数。先给出停止时延目标及测量方法，再验收；已完成与取消的竞态只能产生一个终态，取消后不得继续派发新工具。

## M3：持久化、恢复与幂等

**学习内容**：状态机、事务、检查点、至少一次执行、幂等键、外部副作用与本地提交之间的失败窗口。

**项目工作**：

- 先在 Python 执行层使用 SQLite 保存 run、step、消息、工具调用及结果；Rust 继续承担网关职责。
- 设计如 pending、running、succeeded、failed、cancelled 的运行状态，并定义合法转换和恢复入口。
- 在派发工具前保存调用意图，执行后保存结果；为调用分配稳定标识，恢复时复用已提交结果。
- 分类处理只读、可幂等和不可安全重放的工具。副作用结果不明时进入待核对状态，要求人工确认或业务对账。
- 明确单执行者约束；如引入多个执行者，再增加领取、租约与防止旧执行者写回的机制。

**故障实验与验收**：在“意图落盘后”“工具完成但结果未落盘”“结果落盘后”分别杀死进程并恢复。已提交结果不重复执行；不完整步骤有确定处理策略；未知副作用不会自动重放。用一个支持幂等键的模拟计数工具证明重复请求不会重复加一，同时展示不支持幂等的工具为何无法保证 exactly-once。

## M4：背压、可观测性与证据驱动优化

**学习内容**：有界队列、信号量、排队时间、速率与并发的区别、Little 定律的使用条件、尾延迟、慢消费者、性能剖析。

**项目工作**：

- 在 Rust 网关限制模型调用并发和等待队列；Python 执行层限制活跃 run 和工具并发。若引入服务端 run 调度，先写清新增职责。
- 定义队列满、排队超时和取消的行为；避免无界缓冲，测试慢 SSE 消费者的内存占用。
- 关联 Python、Rust、模型和工具的日志；记录排队时间、模型耗时、工具耗时、运行耗时、活跃数、拒绝数和取消释放耗时。
- 在基本指标稳定后，根据实际需求引入指标导出或分布式追踪；区分“进程存活”与“服务就绪”。
- 先剖析再优化，每次只验证一个假设，例如连接复用、序列化分配或事件粒度；保留收益不足或引入复杂度过高的失败实验。

**故障实验与验收**：

- 分别测试正常负载、突发流量、持续过载、慢上游和慢消费者；队列与活跃任务不突破配置上限，负载下降后服务恢复。
- 既有正常 Mock 基准继续要求零错误及重复性门禁；过载实验单独统计预期拒绝、意外失败和超时，不能混用门禁。
- 比较相同环境与负载下的吞吐、P95/P99、错误、CPU/RSS；至少保留三轮结果。持续过载另补固定到达率实验，避免仅用闭环并发测试掩盖排队问题。
- 优化报告必须包含假设、前后数据、重复性、正确性回归和限制；未测量前不预设“提升百分比”。

## M5：真实模型评测与下一步方向

**学习内容**：任务成功率、工具选择与参数正确性、上下文增长、输入/输出 Token 成本、prefill/decode、KV Cache 和批处理的基本原理。

**项目工作**：

- 建立 20–30 个可复现任务，覆盖文本、单工具、多步工具、参数错误和取消；为任务预先定义评分规则。
- 将用于调试的任务与保留评测任务分开，固定模型标识、采样参数、提示和工具版本；记录模型非确定性，做重复运行。
- 分开报告运行时正确性与模型任务质量；记录 TTFT、任务总时延、工具成功率和实际可得 usage，缺失项标记未知。
- 在预算允许时接入一个真实模型端点做小规模实验；执行前明确调用费用预算。计费单价在实验时核实，不能把 Mock Token 当作真实成本。
- 保留一套可演示的取消、崩溃恢复和过载保护场景，汇总设计取舍与性能报告。

**验收与方向选择**：根据实现过程中的兴趣、独立解释能力和实验成果，在下列方向中选下一季度主线：

| 更有兴趣的问题 | 后续方向 | 下一项实验 |
| --- | --- | --- |
| 任务状态、恢复、工具语义 | Agent runtime/framework | 多执行者恢复、工作流暂停与人工介入 |
| 网络、调度、稳定性、尾延迟 | AI 服务基础设施 | 多 Provider 路由、公平调度、故障隔离 |
| GPU、批处理、显存、生成速度 | 模型推理服务 | 使用现成推理服务建立独立基线，再研究调度 |

不以一次 API 接入证明掌握推理引擎；GPU 内核、训练框架与分布式训练留待方向明确后单独规划。

## 学习方法与每周产出

每个主题按“读原理 → 写设计 → 做最小实验 → 注入失败 → 回归 → 复盘”推进。资料以当前使用组件的官方文档、协议规范和基础论文为主，遇到具体 API 时核对项目锁定版本；不以读完课程数量作为进度。

每周保留四项产出：

1. 一页原理笔记：问题、机制、适用条件和不能保证的事情。
2. 一个能独立运行的实验：成功路径与至少一个失败路径。
3. 一份证据：命令、环境、版本、结果、限制。
4. 一段复盘：为什么采用该设计，替代方案是什么，下周解决哪个问题。

可以让代码助手协助样板代码和实现，但关键状态转换、故障场景、验收标准由自己先定义；在不看生成解释的情况下复述行为，并独立补一个反例。

## 范围控制与维护规则

暂缓 Web UI、多 Agent 编排、插件市场、向量数据库、Kubernetes 和自研推理引擎。只有具体实验暴露需求时再引入，避免外围功能占用运行时主线时间。

每完成一个阶段：运行相关回归，更新架构和已知边界，为关键决策保留简短设计记录，并在本路线图补上完成日期和证据位置。本文更新本身不等于功能完成；历史 QA 和性能数字不能代替当前验证。
